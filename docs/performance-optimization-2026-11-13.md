# BeeCode 大量会话与长内容的性能优化方案

## 结论与适用范围

当目录内会话很多、打开很多标签或单个会话很长时，目前有几条明确随数据量增长的加载、持有和复制路径。优先处理全量会话刷新、非活跃会话的内存预算，以及长会话先完整解析再截取的问题，收益更可能持续；“一键优化”只能缓解可重建缓存占用，不能代替这些改造。

这是一份独立方案，不表示下面的重构已经完成。调查基线为 `fa2f8fc50b610ad118a9f998ccf2a46c0cf5f7ca`；路径行号以该版本为准。专项调查由「规划与审核」助手完成，主会话复核关键路径并整理。

**证据边界：**本次没有采集用户电脑的 heap profile，没有运行已安装桌面应用，也没有读取正式会话或数据库。以下“已确认”指代码结构，不代表已量化它在用户电脑上的占比；不能据此认定内存泄漏，也不承诺改善比例。

## 一、先把三类内存分开

| 层 | 主要内容 | 需要观察的指标 |
| --- | --- | --- |
| WebView / 浏览器 | React、Zustand 会话对象、消息时间线、隐藏标签 DOM、渲染缓存 | JS heap、存活对象、DOM 节点、长任务、交互延迟 |
| Rust 后端 | 会话列表、解析中的文件与消息、摘要缓存、序列化缓冲 | RSS/PSS、分配峰值、请求并发数、解析耗时与响应字节数 |
| 智能体及服务 | 每个 CLI、终端、MCP、由会话启动的服务 | 进程数量、每进程 CPU/RSS、所属目录与生命周期 |

监控里的 RSS 总和可能重复计算共享页，不能当成整机实际独占内存。清掉 Rust 缓存也不会直接释放 WebView 堆或第三方 CLI 的内存。

## 二、已确认的增长路径

### 1. 会话列表是全量查询、全量返回

- 链路：`src/stores/app-workspace-store.ts:405` → `src-tauri/src/commands/conversations.rs:41-105` → `src-tauri/src/db/service/conversation_service.rs:1721-1791`。
- 当前 options 没有分页字段；查询完成后还填充额外摘要信息，再通过 IPC/HTTP 返回。
- `src/components/conversations/conversation-detail-panel.tsx:1281` 等回合边界会触发会话刷新；`src/stores/tab-store.ts:1509-1559` 对新列表重建映射。
- 增长：会话数为 N 时，一次刷新处理 O(N) 条摘要；频繁完成回合会重复付出查询、分配、序列化和前端替换成本。
- 方向：先减少无变化全量刷新，再分页。分页必须同时设计搜索、统计、置顶与跨目录功能，不能把“只加载一页”当成完整兼容方案。

### 2. 每次列表请求都读取 Codex 标题索引

- `commands/conversations.rs:47-61` 每次 `spawn_blocking(load_thread_name_index)`；`src-tauri/src/parsers/codex.rs:385-416` 逐行读取索引。
- 后续 `conversation_service.rs:459-527` 批量查询并尝试刷新标题。
- 增长：索引越大，每次列表请求的额外文件工作越多。
- 方向：按根目录、文件修改时间和大小缓存索引；仅内容变化时同步。保留手工标题锁、环境覆盖、异常重试语义。

### 3. 文件型目录和统计端点重复扫描历史

- `commands/conversations.rs:391-420` 的目录、统计端点复用全量本地会话枚举；例如 `src-tauri/src/parsers/claude.rs:1706-1760` 遍历历史树。
- 摘要缓存命中能减少文件解析，但不能消除目录遍历和每文件 stat。
- 增长：多个端点分别请求时，重复 O(N) 遍历；不能与数据库列表混成同一个端点问题。
- 方向：复用一次扫描结果，短 TTL 或明确事件失效，同一时刻合并重复扫描。按运行实例和 agent 配置隔离缓存键。

### 4. 打开的标签页保留会话内容与 DOM

- `src/components/conversations/conversation-detail-panel.tsx:2935-2951` 将所有标签加入分组；`:3003-3074` 对后台标签使用 `invisible`，不是卸载。
- `heldDetail`（`:541-544`）用于留住已加载详情，避免切换时历史丢失；默认尾窗为 `src/stores/conversation-runtime-store.ts:144` 的 120 轮。
- runtime store 的 `byConversationId`（`:291-299`）没有容量预算；删除主要随标签卸载，后台工作可能延后清理。
- 增长：打开并访问更多会话、向上加载更多页，会保留更多对象。不是所有目录里的会话都会因此自动保留完整消息，不能夸大为“历史总量全部常驻”。
- 方向：给非活跃详情设置预算与最近访问策略。活跃、流式、后台任务、待清理和委派查看中的会话必须豁免。先卸载重渲染子树或释放可重取历史，不直接强制关闭会话/CLI。

### 5. 时间线派生数组与历史翻页增加分配

- `conversation-runtime-store.ts:2406-2464` 的 `PREPEND_OLDER_TURNS` 持续拼接历史，没有累计页数上限。
- `:4283-4286` 派生 `head.concat(tail)` 并放入 `timelineCache`。
- **重要限定：**缓存是 `:3296` 的 `WeakMap`，不是强引用的永久会话表；数组主要复制元素引用，也不能说它把全部消息正文再深拷贝一遍。session 对象仍被 store 持有时，派生数组也继续占用空间。
- 方向：限制加载窗口、分块保存历史、按需要派生时间线。验证虚拟滚动锚点、去重、压缩后窗口失效和后台改写旧消息等既有行为。

### 6. 分钟时钟导致侧栏模型重建

- `src/components/conversations/sidebar-conversation-list.tsx:1439-1443` 每分钟更新 `now`；`:1477-1507` 的可见列表依赖该值，后续分组和索引重新计算。
- virtua 减少的是 DOM，不是全量行模型及过滤的成本。
- **重要限定：**`now` 同时驱动自动归档，不只是相对时间标签。不能简单从列表依赖中删除它，否则静置自动归档会失效。
- 方向：相对时间更新尽量下沉；自动归档改为按下一到期时间调度，或只在归档边界重新计算。用无归档/自动归档两类场景分别验收。

### 7. 流式状态更新复制会话映射

- `conversation-runtime-store.ts:2006-2008` 更新 session 时建立新的 Map；`SET_LIVE_MESSAGE`（`:2918-2949`）处于高频路径。
- 增长：Map 大小时，每次更新的引用复制和 GC 压力提高；正文如何合并还需 profile 量化。
- 方向：按会话分片订阅或把高频 live 状态从全局大 Map 分离；保留 React/Zustand 不变性约定，不原地改 Map 来“优化”。必要时按帧合并展示更新，但完整事件不可丢失。

### 8. 摘要缓存没有容量与淘汰策略

- `src-tauri/src/parsers/summary_cache.rs:91-96,191-197` 使用进程级 HashMap；基线仅插入/替换，没有容量限制和删除路径回收。
- 增长：不同文件越多，占用越大；已删除/改名文件的旧键仍可能保留。
- 本轮监控优化增加显式释放入口，但下一次请求仍可重建缓存，不构成长期内存预算。
- 方向：按估算字节数和条目数双预算的 LRU/闲置淘汰；不存在的路径惰性清理。保持按 agent 命名空间、文件指纹及解析竞态校验。

### 9. 长会话后端先全量解析，再应用窗口

- `commands/conversations.rs:2430-2432` 在完整 detail 上执行窗口；`:2440-2449` 的历史翻页也先取完整 detail 再切片。
- `src-tauri/src/parsers/claude.rs:2896` 使用整文件读取；`src-tauri/src/commands/turn_window.rs:131-138` 在完整 turns 上解析窗口边界。
- 增长：即使前端只请求最近 120 轮，后端峰值仍受整份 transcript 大小影响；并发打开长会话会放大峰值。
- 方向：先限制并发解析/合并相同请求，再做按偏移索引或流式窗口解析。工具调用跨轮配对、压缩、委派元信息和文件重写都会影响正确性，不宜一次性改全部 parser。

### 10. 大工具输出与内联图片进入详情

- `parsers/claude.rs:4129-4156` 提取工具文本，`:4169-4187` 构建图片数据；当前路径没有统一大小预算。
- 增长：单条巨量输出或 base64 图片也能造成解析、IPC 与 WebView 峰值，不能只按“轮数”估算内存。
- 方向：摘要/预览限长，完整输出保留在原文件并按需读取；图片先传引用或缩略图，展开再加载。必须提供“查看完整内容”，不能静默截断原会话、删除文件或让智能体失去完整工具结果。

## 三、已有保护，不建议重复造轮子

- 代码高亮缓存已有预算：`src/lib/code-highlighter.ts:20-30`，16 MB / 128 条。
- 连接有前后端 idle sweep；但打开标签的 keepalive 会影响空闲认定。先测进程生命周期，再决定是否调整，不为省内存终止后台任务。
- 事件流与广播有容量边界：`src-tauri/src/acp/event_stream.rs:18-24`、`src-tauri/src/web/event_bridge.rs:40`。本次没有证明它们是无界队列。
- 消息列表和侧栏已有虚拟化；虚拟化只能限制渲染节点，不能自动限制数据缓存、解析结果或隐藏标签对象。

## 四、分阶段实施工单

| 阶段 | 可独立实施的工单 | 验收重点 |
| --- | --- | --- |
| P0：先降重复工作 | 列表增量 upsert、减少回合边界全量刷新；Codex 索引指纹缓存；同实例扫描 single-flight | 同样的变更只传受影响摘要；手工标题/搜索/归档正确；并发请求不重复扫描 |
| P0：建立预算 | 记录每会话详情/时间线估算量与最近访问时间；非活跃历史按预算回收 | 活跃/后台任务豁免；切回可完整重取；不丢草稿、滚动位置或待确认动作 |
| P1：降低数量成本 | 服务端分页与搜索；summary cache 双预算；历史分块窗口；侧栏分钟更新拆分 | 搜索、置顶、统计不因分页漏项；窗口锚点稳定；自动归档仍按期发生 |
| P1：降低内容成本 | 工具输出按需加载；图片引用化；高频 session 状态分片 | 原始内容无损可查；流式顺序与终态一致；代码/图片交互不回退 |
| P2：针对实测热点 | 单 parser 的窗口解析；非活跃标签快照与重型子树卸载 | 与旧解析结果对照；压缩/重写、后台工具完成、委派恢复均兼容 |

不新增依赖作为默认前提。缓存预算值先基于测量确定，不能凭经验写死一个“最佳”会话数。涉及数据库索引/结构的最终方案需单独确认，本方案不授权迁移。

## 五、可重复的验证方案

### 合成数据与隔离

1. 独立 worktree、独立端口、独立 `CODEG_DATA_DIR` / `CODEG_HOME`、agent 环境根和临时会话目录；逐项核对解析器是否存在回退到真实 HOME 的路径。
2. 禁止用正式数据库、正式 `chat-sessions` 或用户原始会话做写入压测。调试 DB 名称不同不等于聊天目录已隔离；启动前验证真实解析路径和 GC 根目录。
3. 先生成小集合验证读取来源，再扩大规模。清理只针对本次 tempdir。禁止以本轮“一键优化”删除测试之外的数据。

### 数据矩阵

- 元数据维度：会话数 100 / 1,000 / 10,000，各自测试单目录与多目录。
- 内容维度：单会话消息 100 / 1,000 / 10,000；另测 100k 行 transcript、大工具输出、图片和深层工具调用。
- 不需要直接生成所有维度的笛卡尔积（最大可能是亿级消息）；先分别固定其他变量，再按测得拐点选择组合压力场景。
- 标签数 1 / 10 / 30；后台执行数 0 / 1 / 5，防止把第三方 CLI 内存混算为 WebView 问题。

### 操作流程

冷启动 → 目录列表稳定 → 依次打开 N 个会话 → 多次切换目录/标签 → 各向上翻页 → 连续模拟回合完成事件 → 关闭一半标签 → 空闲观察 → 一键优化 → 再次打开已释放的历史。

每组至少重复 5 次，记录冷/热缓存差异；空闲观察保持相同时间窗口。测量需固定版本、平台、硬件、依赖版本、窗口大小与数据种子。

### 指标与判据

| 指标 | 采集建议 | 不能混淆的边界 |
| --- | --- | --- |
| WebView heap / retained objects | 桌面平台可用的 WebView profiler；浏览器用 DevTools heap snapshot | Chromium 结果不能代替 macOS WKWebView 验证 |
| 后端与 agent RSS/PSS | Linux `/proc/<pid>/status`、`smaps_rollup`；macOS/Windows 对应进程工具 | 多进程 RSS 求和可能重复共享页 |
| 请求耗时与载荷 | 列表/详情/翻页记录 P50/P95、响应字节、解析并发峰值 | CPU 首次采样及缓存冷启动单列 |
| 交互与渲染 | 标签切换 P95、长任务、侧栏分钟 tick 耗时、节点数 | JS heap 下降与用户感知变快是不同指标 |
| 资源回收 | 关闭标签/优化前后对象与稳态内存 | 分配器未立刻归还 RSS 不等于对象仍泄漏 |

先建立数值基线，再约定绝对预算与回归阈值。结构性验收可以先固定：单条摘要变更不触发全量列表传输；相同并发扫描只执行一次；非活跃缓存超过预算后不继续线性增长；淘汰后会话内容可恢复且无数据损失。当前没有实测数值，不填写虚构的耗时、MB 数或改善百分比。

## 六、本轮一键优化的实际边界

本轮只释放 BeeCode 可重建的摘要内存缓存。返回条目数和已知字符串容量的保守估算；磁盘回收为 0，明确提示没有删除磁盘数据。并发请求可以在之后重新构建缓存，系统分配器不保证 RSS 立即下降。

未纳入：系统页面缓存、浏览器完整堆、运行中的智能体进程、用户会话/附件、代理二进制、下载运行时与未知临时目录。若要扩展磁盘回收，另做可识别所有权、闲置判断、预览、确认和失败重试设计，不把通用目录删除包装成“一键优化”。
